fix: stop discarding chart axis-tick decimals for large numbers

`formatAxisTick` forced every axis tick at or above magnitude 10 to 0 decimal places, no matter what a tile's Number Format configured. Once a value is abbreviated to `k`/`m`/`b`/`t` (which happens for any tick in the thousands or higher), that forced rounding threw away precision the abbreviated label had room for — two ticks like 950 and 1080 both rendered as `1k` instead of something like `950`/`1.08k`. Axis ticks now search downward from the configured decimal places for the most precision that still fits the label's width budget, instead of always rounding to a whole number — this now applies uniformly at every magnitude, and correctly ignores a byte tile's `MB`/`GB` unit suffix when measuring width, so nearby byte values (e.g. `1.2 GB` vs `1.4 GB`) no longer collapse into the same rounded label either. Two follow-up fixes to that same width check: a small negative percentage like `-0.01%` no longer collapses to `-0%` (a negative sign and a `%` suffix together need one more character than either alone), and a data-rate tile with a long unit suffix like `Gibit/s` now falls back toward fewer decimals instead of overflowing the axis, since the unit suffix is budgeted rather than ignored outright. The axis's 40px column only has room for the same handful of characters regardless of what a suffix says (the tick font is monospace), so a byte/data-rate/throughput tile with an auto-scaling Number Format unit (e.g. `GiB`, the default for byte tiles in the UI) still renders as a whole number rather than gaining a decimal; that's an intentional, width-safe fallback (an overflowing right-anchored SVG label clips off-canvas into a truncated, differently-misleading number), not a bug. A *fixed* unit (one whose suffix is the same on every tick, like `cps` — the default for throughput tiles) drops that suffix from the axis label entirely instead, since a constant suffix carries no information there, spending the whole budget on precision (`0.25 cps` now shows `0.25`, not `0`).

Separately, even with full precision, a tile whose Y-axis is fit tightly to a narrow data range (`Fit Y-Axis to Data` on, with a coarse configured mantissa) could still show duplicate tick labels — Recharts generates its own tick values from the domain with no awareness of how many distinct labels are actually achievable at that mantissa. The Y-axis now retries with fewer ticks (using the same fixed-domain generator Recharts itself uses for a concrete domain) until every label is distinct, instead of leaving Recharts to render two ticks with the same text — dropping duplicates from a fixed-size set instead would leave the survivors unevenly spaced. If no tick count helps distinguish the range at all, it keeps the full, redundant set rather than reduce the axis to one tick, since that would misrepresent the chart as flat.
