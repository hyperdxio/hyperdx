fix: stop discarding chart axis-tick decimals for large numbers

`formatAxisTick` forced every axis tick at or above magnitude 10 to 0 decimal places, no matter what a tile's Number Format configured. Once a value is abbreviated to `k`/`m`/`b`/`t` (which happens for any tick in the thousands or higher), that forced rounding threw away precision the abbreviated label had room for — two ticks like 950 and 1080 both rendered as `1k` instead of something like `950`/`1.08k`. Axis ticks now search downward from the configured decimal places for the most precision that still fits the label's width budget, instead of always rounding to a whole number — this now applies uniformly at every magnitude, and correctly ignores a byte tile's `MB`/`GB` unit suffix when measuring width, so nearby byte values (e.g. `1.2 GB` vs `1.4 GB`) no longer collapse into the same rounded label either. Two follow-up fixes to that same width check: a small negative percentage like `-0.01%` no longer collapses to `-0%` (a negative sign and a `%` suffix together need one more character than either alone), and a data-rate tile with a long unit suffix like `Gibit/s` now falls back toward fewer decimals instead of overflowing the axis, since the unit suffix is budgeted rather than ignored outright. The axis's 40px column only has room for the same handful of characters regardless of what a suffix says (the tick font is monospace), so a byte/data-rate/throughput tile with a configured Number Format unit (e.g. `GiB`, `cps`) — the default for byte tiles in the UI — still renders as a whole number rather than gaining a decimal; that's an intentional, width-safe fallback, not a bug. A tick under 1 with a unit suffix (e.g. `0.25 cps`) also still renders as `0` for the same reason — a right-anchored SVG label past the width budget clips off-canvas rather than merely overlapping, which would show a truncated, misleadingly different-looking number, so there's no safe way to rescue it here.

Separately, even with full precision, a tile whose Y-axis is fit tightly to a narrow data range (`Fit Y-Axis to Data` on, with a coarse configured mantissa) could still show duplicate tick labels — Recharts generates its own tick values from the domain with no awareness of how many distinct labels are actually achievable at that mantissa. The Y-axis now computes its own tick values (clamped to the domain, since Recharts' own "nice" values can otherwise land just outside it) and drops any tick whose label would repeat the previous one, instead of leaving Recharts to render two ticks with the same text.
